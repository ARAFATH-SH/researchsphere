# Decisions

One entry per decision: the date, what was decided and why. Add to the end; do not rewrite
old entries. To change a decision, add a new entry that replaces the old one.

| Date | Decision | Reason |
| --- | --- | --- |
| 2026-10-05 | The API server is one Go application divided into modules (a modular monolith). Only the sync, compile and AI services are separate. | One developer; fewer moving parts to deploy and debug. A module can become its own service later. |
| 2026-10-05 | Embeddings are stored in PostgreSQL with pgvector, not in a separate vector database. | One database to run and back up; enough for 10,000 profiles (NFR-1). |
| 2026-10-07 | Requirements live in `docs/SRS.md`, and every slice names the requirement IDs it covers. | Keeps code traceable to requirements. |
| 2026-10-07 | The local PostgreSQL container listens on port 5433. | Port 5432 may already be used by a PostgreSQL installed on Ubuntu. |
| 2026-10-08 | Top-level folders are `frontend/`, `backend/`, `ai/`, `sync/`, `compile/` and `docs/`. | Each service is easy to find, and each can be built and deployed on its own. |
| 2026-10-08 | Project instructions for AI assistants are in `AGENTS.md`. The repository has no `CLAUDE.md`. | Claude Code reads `AGENTS.md` when no `CLAUDE.md` exists; one file avoids two sets of rules. |
| 2026-10-08 | CI is one GitHub Actions workflow, `.github/workflows/ci.yml`. A `detect` job runs the backend, frontend and ai jobs only when `go.mod`, `package.json` or `pyproject.toml` exists, and fails when a folder has source files but no manifest. | Jobs stay green before any code exists, and a missing manifest cannot make real code skip its checks. |
| 2026-10-08 | CI uses golangci-lint v2.14.0. Actions are pinned to a major version, except `astral-sh/setup-uv`, which is pinned to an exact release because it publishes no major tags. | Same linter version as on the developer's machine; major pins get fixes without surprise breaking changes. |
| 2026-10-09 | Embeddings are `vector(768)`. A model with another output size needs a new migration and a full re-embed. | 768 fits SPECTER2 and all-mpnet-base-v2, so either can be chosen in the AI-1 slice; HNSW indexes need a fixed size. |
| 2026-10-09 | Sessions (refresh tokens) and one-time tokens (verification, reset) are PostgreSQL tables, added to SRS section 7. Login lockout (FR-2.7) and rate limits (NFR-8.3) are Redis counters, not tables. | Sessions must survive a Redis restart (30-day tokens); counters are short-lived and expire on their own. |
| 2026-10-09 | "Exactly one owner per project" is enforced in the database: a partial unique index allows at most one, and a deferred constraint trigger requires one at commit. | The SRS requires the rule in the database. Deferring the check lets a project and its owner, or an ownership transfer, be written in one transaction. |
| 2026-10-09 | Down migrations remove everything their up file created, extensions included. CI applies all migrations, undoes them, checks that the public schema is empty, and applies them again. CI installs golang-migrate v4.18.3 and checks its sha256. | NFR-11.1 requires migrations that can be undone; the check catches a down file that misses something. |
| 2026-10-09 | The API server uses the standard library `net/http` server and `ServeMux`, with no web framework. Routes and types are generated from `docs/openapi.yaml` by oapi-codegen (`std-http-server` and `strict-server`), and handlers implement the generated strict interface. | Go 1.22 routing patterns are enough; the strict interface lets a handler return only responses the contract declares. |
| 2026-10-09 | Generated code (`backend/internal/api/api.gen.go`) is committed. CI regenerates it and fails when it differs. oapi-codegen is pinned with a `tool` directive in `backend/go.mod` and run with `go tool`. | Code review shows the generated changes; one pinned generator version gives the same output locally and in CI. |
| 2026-10-09 | The backend uses `jackc/pgx/v5` (pgxpool) for PostgreSQL and `redis/go-redis/v9` for Redis. `backend/go.mod` says `go 1.26`, because go-redis v9.23 requires it. | pgx/v5 is the driver sqlc generates for; go-redis serves the Redis counters (lockout, rate limits). |
| 2026-10-09 | The CI stack job runs only the database tests (`make test-db`). Go lint, tests and the generated-code check run in the backend job. | Go checks need no database; running them in one job avoids running them twice. |
| 2026-10-09 | Every error, including unknown routes (404), wrong methods (405) and recovered panics (500), uses the shape `{"code", "message"}`. The server makes a new request ID for every request, returns it in `X-Request-ID`, and ignores one sent by the client. | SRS 5.3 requires one error shape; an ID chosen by the client could forge log lines. |
| 2026-10-09 | Inside the modular monolith, each backend module follows clean architecture: `domain` (entities and interfaces, standard library only), `usecase` (business logic, imports only its own domain) and `adapter/http`, `adapter/postgres`, `adapter/redis`. Shared code is in `internal/platform`, generated code in `internal/api/gen`, and only `cmd/api` wires them together. golangci-lint's depguard enforces the dependency rule, with one `usecase-<module>` rule per module. Layers are created only when they have code. The health check is the reference module. | Business logic stays testable with fakes and free of HTTP and database details; a lint rule keeps the layering from eroding as one developer adds 30 slices. |
| 2026-10-09 | The web client is Next.js 16 (App Router) with TypeScript strict mode, Tailwind CSS 4 and ESLint, installed with npm. Node.js 22 is pinned in `frontend/.nvmrc`, and CI reads its version from that file. | One Node version locally and in CI; `create-next-app` defaults keep the setup standard. |
| 2026-10-09 | TypeScript types for the API are generated from `docs/openapi.yaml` by openapi-typescript into `frontend/src/lib/api/schema.gen.ts`, which is committed. All calls go through one openapi-fetch client in `frontend/src/lib/api/client.ts`. `make generate` regenerates the Go code and these types; CI fails when either is out of date. | The client and server are typed from the same contract (SRS 5.3); openapi-fetch is a small runtime that types paths, parameters and responses from the generated file. |
| 2026-10-09 | The browser calls `/api/v1` on the web client's origin, and a Next.js rewrite forwards it to `API_URL` (default `http://localhost:8080`). The API server needs no CORS. | No cross-origin requests; the API address stays on the server. Rewrites are fixed at `next build`, so a production build needs `API_URL` set; hosting is still open (SRS 8.2). |
| 2026-10-09 | Frontend tests use Jest with `next/jest` (SWC) and React Testing Library, in jsdom. The config is `jest.config.mjs`, not `.ts`, so that Jest needs no `ts-node`. | Jest is the runner named in the proposal; `next/jest` needs no Babel setup. |
| 2026-10-10 | Passwords are hashed with Argon2id (`golang.org/x/crypto/argon2`): 19 MiB of memory, 2 passes, 1 thread, a 16-byte random salt and a 32-byte key, stored in the PHC string format (`$argon2id$v=19$m=19456,t=2,p=1$salt$hash`). Passwords are 8 to 128 characters. | OWASP's first choice; memory-hard, so it resists GPU cracking better than bcrypt, and it has no 72-byte input limit. The PHC string records the parameters, so they can be raised later without breaking stored hashes. |
| 2026-10-10 | SQL queries are generated with sqlc, pinned by a `tool` directive in `backend/go.mod` and run through `go generate`. Settings are in `backend/sqlc.yaml`; the schema is read from the migrations. Each module's generated code is committed in `internal/<module>/adapter/postgres/sqlcgen`, with `omit_unused_structs` so it holds only the types its queries use. | Queries are checked against the schema at generation time and always take parameters (NFR-8.1). One pinned version gives the same output locally and in CI, as for oapi-codegen. |
| 2026-10-10 | One-time tokens are 32 random bytes in base64url. Only their SHA-256 is stored. A verification link carries the token in the URL fragment (`/verify-email#token=...`), and the page posts it to the API. Asking for a new verification link deletes the user's unused verification tokens. | NFR-5 requires hashed tokens; 256 random bits need no salt or slow hash. A browser never sends the fragment to a server, so the token stays out of access logs and Referer headers. Only the latest link works. |
| 2026-10-10 | Local email goes to Mailpit (`axllent/mailpit`, pinned to an exact version) in `docker-compose.yml`: SMTP on 127.0.0.1:1025, inbox on 127.0.0.1:8025. The API sends through a `Mailer` interface with an SMTP adapter on `net/smtp`, using STARTTLS when the server offers it. | No real email leaves a developer machine, and the inbox shows every message. Production SMTP (login, required TLS) is settled when hosting is chosen (SRS 8.2). |
| 2026-10-10 | This replaces the entry of 2026-10-09 about the CI stack job. The stack job runs `make test-db` and then the Go repository tests (`make test-integration`, build tag `integration`) against the migrated database. Go lint, unit tests and the generated-code check stay in the backend job. golangci-lint lints the `integration` files too. | Repository tests need the real schema and its constraints (citext, CHECKs, transactions); the stack job already has the migrated database, so the backend job still needs none. |
| 2026-10-10 | The web client follows `docs/ui-guidelines.md`: the layout patterns of a professional network (warm gray page, white cards, pill buttons, a top bar with icon tabs, a bottom bar below 768px) with our own name, logo and deep indigo `#3b4cca`. Colors are Tailwind `@theme` tokens in `globals.css`. The theme is light only for now. Icons are inline SVG; there is no icon library. | Users know the pattern from the sites they already use; tokens keep colors in one place. One theme is easier to get right first; inline icons avoid a dependency for seven shapes. |
| 2026-10-10 | Pages are split into two route groups that do not change URLs: `app/(public)` (landing, register, check-email, verify-email, login, reset-password) with the signed-out top bar, and `app/(app)` (every other page) inside the signed-in shell. The shell checks no session until login exists (slice 8). | Each group has one layout; slice 8 adds the session check to `(app)/layout.tsx` only. |
| 2026-10-10 | The register form has a "Confirm password" field that is checked only in the browser. The API keeps `{fullName, email, password}` (FR-1.1). The check-email page is at `/check-email`; `/register/check-email` redirects there. | Catches typos in a password the user cannot see, without changing the contract. |
| 2026-10-10 | This replaces the indigo palette in the entry above about `docs/ui-guidelines.md`. The theme mixes a professional network and a research network: background `#F5F6F4`, surface `#FFFFFF`, border `#E1E4E8`, text `#1F2933`, text-muted `#5F6B7A`, primary deep teal `#0B7A75` (hover `#09615D`, soft `#E6F3F2`), secondary deep blue `#1F4E8C`, danger `#C62828`. Components use only these Tailwind tokens. Light theme only. | A research-flavoured identity that is our own, not LinkedIn's blue or ResearchGate's teal; every text pair passes WCAG AA. |
| 2026-10-11 | Page width is set only by `frontend/src/components/Container.tsx` (`docs/ui-guidelines.md`, Layout widths): 1280px for signed-out pages, 1128px for signed-in pages, full width for the workspace, with side padding of 16, 24 and 32px. Sections never set a max-width. The auth pages (register, check-email, verify-email, login, reset-password) sit in a nested route group `app/(public)/(auth)` whose layout puts them in the Container, so landing sections can be full-bleed. URLs do not change. | One component keeps widths consistent, and a wider marketing page uses large screens better. Full-bleed backgrounds need a `main` that has no width of its own. |
| 2026-10-13 | Access tokens are JWTs signed with HS256 by `github.com/golang-jwt/jwt/v5`, holding only `sub` (user ID), `iat` and `exp`, valid for 15 minutes. The key is `JWT_SECRET` (at least 32 bytes). Checking a token accepts only HS256 and requires `exp`. Refresh tokens are 32 random bytes in base64url, like one-time tokens; each login adds a row to `sessions` holding only the token's SHA-256. | A small library with no dependencies of its own that enforces the algorithm and expiry, so the project writes no JWT parsing. One server signs and checks, so a shared secret is enough. |
| 2026-10-13 | Login sets two cookies, both `HttpOnly` and `SameSite=Lax`: `rs_access` (path `/`, 15 minutes) and `rs_refresh` (path `/api/v1/auth`, 30 days). They are `Secure` when `APP_BASE_URL` starts with `https://`. The login response is `Cache-Control: no-store`. | Scripts cannot read the tokens. The refresh token is sent only to the auth routes. Local work over http still gets cookies with no extra setting, and production must use HTTPS anyway (NFR-5). |
| 2026-10-13 | `docs/openapi.yaml` sets `security: [cookieAuth]` at the top level, so every operation needs a session unless it declares `security: []` (FR-3.1). oapi-codegen's `enable-auth-scopes-on-context` compatibility option marks secured operations in the request context (`gen.CookieAuthScopes`), and `httpx.RequireAuth` checks the `rs_access` cookie only there. Its 401 uses the code `unauthenticated`. | The contract stays the only list of public operations, and a new operation is protected by default. The option is deprecated upstream because it cannot express OR or AND combinations of schemes; this API has one scheme. If a later oapi-codegen removes the option, move to its request-validation middleware. |
| 2026-10-13 | Login answers `invalid_credentials` (401) for both an unknown email address and a wrong password. It answers `email_not_verified` (403) only after the right password. For an unknown address it still checks the password against a dummy Argon2id hash. | Neither the answer nor the response time reveals whether an account exists (FR-2.1, FR-1.4). |
| 2026-10-13 | `POST /auth/refresh` rotates the refresh token on every use: the session row gets the new token's hash, and the old hash moves to `session_retired_tokens`. The session keeps the expiry it got at login (30 days); refreshing does not extend it. A retired token sent again ends (revokes) its session, with no grace period, so the web client must never send two refreshes at once. Refresh and logout are public operations (`security: []`) that rely on the `rs_refresh` cookie; a refused refresh answers `session_invalid` (401) for every reason and clears both cookies. Logout revokes only the session in the cookie and always answers 204. Retired hashes are not cleaned up yet; they go when the session or the user is deleted. | Rotation with reuse detection turns a stolen refresh token into a short-lived one: whichever of the thief and the user refreshes second ends the session. A fixed expiry matches FR-2.1 (refresh tokens last 30 days). After logout the access token stays valid until it expires (at most 15 minutes) because it is checked without the database; its cookie is cleared. |
