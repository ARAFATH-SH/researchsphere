| 2026-10-13 | `POST /auth/refresh` rotates the refresh token on every use: the session row gets the new token's hash, and the old hash moves to `session_retired_tokens`. The session keeps the expiry it got at login (30 days); refreshing does not extend it. A retired token sent again ends (revokes) its session, with no grace period, so the web client must never send two refreshes at once. Refresh and logout are public operations (`security: []`) that rely on the `rs_refresh` cookie; a refused refresh answers `session_invalid` (401) for every reason and clears both cookies. Logout revokes only the session in the cookie and always answers 204. Retired hashes are not cleaned up yet; they go when the session or the user is deleted. | Rotation with reuse detection turns a stolen refresh token into a short-lived one: whichever of the thief and the user refreshes second ends the session. A fixed expiry matches FR-2.1 (refresh tokens last 30 days). After logout the access token stays valid until it expires (at most 15 minutes) because it is checked without the database; its cookie is cleared. |
| 2026-10-13 | The auth cookies depend on the same-origin rewrite of 2026-10-09, which stays: the browser calls only `/api/v1` on the web client's origin, never the API port, and the API server gets no CORS and no `credentials: "include"`. | 2026-10-13 | Login lockout (FR-2.7) counts failed logins per account in Redis (`internal/auth/adapter/redis`, behind the `domain.LoginAttempts` interface). The key is the SHA-256 of the email address in lower case, so no address is stored in Redis and letter case cannot get round the lock. A wrong password and an unknown address both count. A malformed address is not counted, and neither is the right password on an unverified address. The window is fixed: it starts at the first failure and lasts 15 minutes (`INCR`, then `PEXPIRE NX`). The 5th failure in a window locks the account for 15 minutes from that failure. While locked, every login is refused with `account_locked` (429, `Retry-After` in seconds, a message giving the minutes left) before the password is checked, and those attempts neither count nor extend the lock. Only a login that starts a session clears the counter. **When Redis fails or does not answer within 300ms, the usecase logs one warning and allows the login**, skipping the counter for the rest of that login. Every counter call has a 300ms deadline (`callTimeout`, a constant in the adapter, not a setting). The adapter uses its own go-redis client, made from the shared client's address and credentials, with `ContextTimeoutEnabled`, a pool of 5, no retries (`MaxRetries: -1`, because go-redis reads 0 as 3), and dial, read and write timeouts of 300ms. `cmd/api` closes it at shutdown. The shared client is unchanged. | Counters are short-lived and expire on their own (entry of 2026-10-09). Failing open keeps a Redis outage from locking every user out; the cost is that during an outage there is no lockout, which the warnings show. The shared client ignores context deadlines and waits up to 5s per call for a Redis that hangs, so a deadline on the context alone did not shorten the wait; a separate client keeps the health check and later Redis users on their own settings, and a small pool caps the connections a hung Redis can tie up. Counting unknown addresses keeps the answer from revealing which accounts exist. Because FR-2.7 locks per account, anyone who knows an address can lock that account for 15 minutes; per-IP limits (NFR-8.3) are a separate slice. |
| 2026-10-13 | Password reset (FR-2.3 to FR-2.5). `POST /auth/password-reset/request` answers 202 for every well-formed address; for an existing account, verified or not, it deletes the account's unused reset tokens and emails a link to `/reset-password#token=...` (the fragment, as for verification links) that works once for 1 hour. `POST /auth/password-reset/confirm` applies the registration password rule (8 to 128 characters) and, in one transaction, marks the token used, stores the new Argon2id hash, marks the email address verified and revokes every session of the account. After the commit it clears the account's failed-login counter in Redis (FR-2.7); a failure there is logged and does not fail the reset. It does not lift an active lock. Access tokens already issued stay valid until they expire (at most 15 minutes). Both operations are public. | The fragment keeps the token out of access logs and Referer headers. Only the latest link works. Opening the emailed link proves the user reads that inbox, the same proof verification uses, so an unverified account can sign in after a reset. Ending every session means a thief holding a refresh token loses it (FR-2.5). Redis cannot join the database transaction, and the lockout already fails open. |
| 2026-10-14 | Change password (FR-2.6, FR-2.5). `POST /auth/password` needs a session. The server finds the current session from the `rs_refresh` cookie, which its `/api/v1/auth` path already sends; the access token is unchanged. In one transaction it locks that session row, stores the new Argon2id hash and revokes every other session of the user. When the cookie is missing or names no live session of this user, every session ends. Checks run in this order: account lock (FR-2.7, `account_locked` 429 before any password check), new password length (8 to 128), current password (`wrong_current_password`, 400), then new equal to current (`same_password`, 400). A wrong current password counts as a failed login in the same Redis counter, keyed by the account's email address, so 5 failures from login and this operation together lock the account. A successful change clears the counter. Wrong current password is 400, not 401, because the web client answers a 401 by refreshing the session. The page is `/settings/account` in the signed-in shell, reached from the "Me" menu, with no shared settings layout until a second settings page exists. | Reusing the refresh cookie keeps the current device signed in without putting a session ID in the JWT. Sharing the login counter means the operation cannot be used to guess passwords at a faster rate than login. Comparing new with current only after the current password is verified means a guess is always counted. Locking the session row keeps a refresh that runs at the same moment from rotating its hash mid-change. |
| 2026-10-14 | Delete account (FR-2.8, FR-2.9). Projects where the deleting user is the only member are deleted with the account; shared projects block deletion (FR-2.9). `DELETE /account` needs a session and takes `{password}`. Checks run in this order: account lock (`account_locked` 429 before any password check), password (`wrong_password`, 400, counted as a failed login in the shared Redis counter, as for change password). Then, in one transaction: lock the projects the user owns (`SELECT … FOR UPDATE`), look for those with other members and refuse with `owns_shared_project` (409, listing their IDs and titles) if there are any, delete the solo projects, remove the user's `user_publications` rows, delete the publications that no longer have any author, and delete the user row; the schema's cascades remove the profile, posts (with other users' comments and likes on them), comments, likes, connections, sessions, tokens, embeddings, project memberships and notifications. A publication still linked to another user stays. After the commit the failed-login counter is cleared and both session cookies are cleared. The account is deleted outright (hard delete); an access token already issued on another device stays signed but every operation that reads the user answers 401 `unauthenticated`, so that device is sent to `/login`. The settings page leaves with a full page load to `/` and shows "Your account was deleted" once, from a `sessionStorage` note. | SRS 7 says deletion removes personal data at once and that "publications shared with a co-author stay for that co-author", which implies unshared ones go. Locking first and checking in a later statement means a member who joins during the deletion is seen (a new member row takes a key-share lock on its project, which waits for the lock); publications are locked the same way before their links are removed, so a co-author who links one at the same moment keeps it. Sharing the login counter and checking the lock first keep this operation from being a faster way to guess a password. 400, not 401, for a wrong password because the web client answers a 401 by refreshing the session. A full page load drops the tab's in-memory session; marking it signed out on the page would make the signed-in shell send the user to `/login` instead. |

| 2026-10-16 | Suspended accounts (FR-3.4). `users.suspended_at` set means suspended; until slice 27 (FR-15.3) it is set directly in the database. Login checks the account lock first, then the password, then suspension, then email verification: a suspended account with the right password gets `account_suspended` (403, "This account is suspended. Contact support."), which is not counted as a failed login; a wrong password gets the usual `invalid_credentials` (401) and is counted. `POST /auth/refresh` reads the user's `suspended_at` in the same locked session query; for a suspended account it revokes that session and answers `session_invalid` (401), like any other refused refresh. Suspension therefore takes effect at the next refresh, so an existing login ends within 15 minutes, when its access token expires, the same as account deletion. There is no access-token denylist. `POST /auth/password-reset/request` still answers 202 but stores no token and sends no email for a suspended account (FR-2.4). `POST /auth/password-reset/confirm` refuses a suspended account with `account_suspended` (403) and changes nothing; the token stays unused. | Checking the password first means the answer reveals a suspension only to someone who knows the password. Checking at refresh needs no extra lookup on every request and keeps access tokens checked without the database (entry of 2026-10-13); 15 minutes is an accepted delay. Naming the suspension on reset confirm reveals nothing new, because the token proves the caller reads the account's inbox. |
| 2026-10-17 | Permissions live in `internal/platform/authz` and mirror SRS 2.3; every endpoint uses it (FR-3.2). `authz.Can(role, action)` holds the "Platform level" table and `authz.CanInProject(projectRole, action)` the "Project level" table, one action constant per row, each naming its row. Anything not in a table is refused: an unknown role or action, and the empty role. `CanInProject` does not take the platform role, so an administrator has no extra rights inside a project. `httpx.RequirePlatform(action)` guards an operation with a platform action; project handlers will call `CanInProject` with the role from `authz.ProjectRoleLookup`, which has no implementation until slice 19. Every refusal is 403 with exactly `{"code":"forbidden","message":"You do not have permission to do this."}` (`httpx.WriteForbidden`), with no resource data and no reason (FR-3.3). Account self-service (`GET /auth/me`, `POST /auth/password`, `DELETE /account`) needs only a valid session and no `RequirePlatform`: these operations act only on the caller's own account, so every logged-in role (researcher, admin) may use them. They are not the "Edit own profile" row, which belongs to the profile module (slice 10). | One package that copies the SRS tables cell by cell, with a test per cell, makes a wrong permission a failing test rather than a review comment. Leaving the platform role out of `CanInProject` makes the SRS 2.3 note impossible to break by accident. One fixed refusal body cannot leak what was refused or why. |
| 2026-10-17 | The access token carries the user's platform role in a `role` claim (`researcher` or `admin`, from `users.role`), signed at login and at refresh. This amends the entry of 2026-10-13, whose token held only `sub`, `iat` and `exp`. `httpx.RequireAuth` puts the role in the request context next to the user ID; the role is never read from the request body or a header. A token without a `role` claim is invalid (401), so a token signed before this change makes the web client refresh once. **A role change takes effect at the next refresh, up to 15 minutes later**, the same as suspension and account deletion. | Access tokens stay checked without the database (entry of 2026-10-13), so a permission check costs no query on every request. The role is covered by the HS256 signature, so a client cannot change it. The 15-minute delay is already accepted for suspension and account deletion. |
| 2026-10-17 | Administrators are made only from the command line: `make admin email=...` sets `users.role = 'admin'` and `make unadmin email=...` sets it back to `'researcher'` (`backend/cmd/setrole`, one sqlc query). No API operation changes a role, and the store method is not part of `domain.Store`, so no handler can reach it. The role is signed into the access token, so a change takes effect at the user's next refresh (within 15 minutes) or login; existing sessions are not ended. `GET /auth/me` (and the login response) return the role so the web client can show the Admin tab; the tab and the `/admin` redirect are only convenience, and the API stays the protection.
